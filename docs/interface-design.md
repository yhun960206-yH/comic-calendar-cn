# 漫展日历：订阅首页设计依据

本次调整直接作用于 `src/site.py` 与 `src/assets/`，由构建器生成真实页面；不是另一个孤立的设计样稿。

## 1. 谁来用、什么时候用

- **主要用户**：在手机上看漫展信息、但不一定知道 ICS 是什么的普通观众。想关注自己的城市，而不是研究日历协议。
- **主要场景**：看到站点链接 → 找到自己的城市 → 复制 URL → 在常用日历里订阅 → 日后核对活动来源。用户可能只花一两分钟，不愿注册账号。
- **次要场景**：已知道活动名称的观众阅读详情；没有本地活动的观众先订阅，等待将来收录。

因此首页首先回答“能做什么”和“从哪开始”，而不是堆出 372 个入口或先展示活动卡片。

## 2. 页面每一步为什么这样排

| 步骤 | 页面决定 | 原因与边界 |
| --- | --- | --- |
| 进入 | 首屏一句用途说明 + 唯一突出按钮「选择城市」 | 不要求理解 ICS，也不把浏览活动误认为主任务；提示这不是购票或报名。 |
| 找城市 | 搜索省份／城市（兼容省市后缀）+ 可展开的完整城市目录 | 372 个城市全部可达，但初次打开不铺满屏幕；无脚本时仍能展开目录，用原生锚点进入城市。 |
| 得到链接 | 所选城市的订阅地址和「复制订阅链接」紧挨着展示 | 主动作和结果放在同一位置；复制失败时还能直接打开或手动选中链接。零活动城市也允许订阅。 |
| 完成订阅 | 明确告知“复制后还须在日历应用中通过 URL 添加”，再提供 Apple／Google 网页／Outlook 网页的折叠说明与官方链接 | 避免将“复制了”误说成“已经订阅”；只针对有官方依据的平台给出操作入口，不承诺所有客户端步骤相同或刷新即时。 |
| 查看内容 | 订阅之后才列出当前已收录活动，链接到详情；空城单独提示 | 活动是订阅服务的内容而非首页竞争动作；不凭空补活动或票务。 |
| 建立预期 | 收录比例、来源观察／人工核对时间、覆盖限制放在页面尾部，也在空状态及详情中保留 | 372 条日历地址不等于 372 个城市有活动；来源核对时间不是部署时间，也不保证公告始终有效。 |

## 3. 视觉决策

留白用于分隔任务阶段，而不是装饰：首屏独立、城市搜索与订阅由细线分段、活动列表采用文字行而非一排卡片。低彩度背景与单一深色按钮让**订阅操作**比背景更显眼。手机端单列、按钮全宽，目录限制高度；详情页沿用同一排版和订阅入口。未复制第三方标志、配图或原站代码。

## 4. 验证与尚未保证的事

构建器和单元测试检查空城说明、城市顺序、真实 HTTPS 链接、详情转义、DEMO 警告与客户端说明。浏览器中的实际日历订阅／刷新时间由 Apple、Google、Outlook 等客户端决定，未在本地构建时验收；数据来源的完整性和活动公告后续更改也不是页面设计能保证的。
